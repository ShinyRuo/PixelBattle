《忍法战场》复刻版。Godot 4.7.2 / GDScript / 2D 像素风 / PC + 手机双端 / 无限流 PVE。

## 00 决策记录

### 已锁定

| 项 | 决策 | 理由 / 影响 |
|---|---|---|
| 引擎 | Godot 4.7.2 + GDScript | 开源、双端导出成熟、自定义 Resource 白送数据编辑器 |
| 平台 | PC（Steam）+ 手机（Android） | 系统层共用，UI 做自适应而非两套 |
| 画风 | 2D 像素风，`640×360` viewport | 工程既定（`stretch/mode=viewport`） |
| 屏幕方向 | **统一横屏** | 阵型有纵深，横屏表达更好；一套布局；手游自走棋横屏已是惯例 |
| 模式 | 只做无限流 PVE | 砍 PVP：冷启动匹配池不足、同步成本高 |
| 局时结构 | 无限波次 + 波次间隙可断点 | 手机端刚需，PC 端是崩溃兜底 |
| 题材 | 火影主题，复刻原版羁绊 | 角色数据全部进 Resource，代码只认 id，换皮 = 改 `data/` |
| 手动干预 | 大招自动寻优 + PC 可手动指定 | 双端分层，见 §02 |

### 未定

- **商业化** —— 买断制、免费+内购、还是先做作品集。本文档按**买断制、无内购**写，
  所有经济都是局内闭环，将来改变现模式不用推翻结构。
- **同屏单位上限** —— 与像素分辨率冲突，见 §04。**开工前必须定。**
- **先出哪一端** —— 建议 **PC 先行**：调试链路短、迭代快。手机版在玩法定型后再适配。

### 相对原版的四处主动改动

1. **任务派遣改为「羁绊 ↔ 金币」取舍**（§06）。原版「放两个人就给钱」是纯操作税，
   改造后成为第二条核心张力轴。**这是本案最大的原创赌注。**
2. **吸怪分层保留**（§02）。手机端大招自动寻优，PC 端可手动指定落点。
3. **角都取消输出能力**（§07）。原版他兼任经济位与雷系 AOE 第二，是明确的平衡漏洞。
4. **波型交替**（§04）。潮水波 / 精英波让 AOE 与单体输出各有高光，
   回应原版「无尽只堆数值」的批评。

## 01 单局结构与会话

### 波次循环

一波 = 准备阶段 + 战斗阶段。准备阶段**不限时**。

| 阶段 | 时长 | 玩家可做 | 可否退出存档 |
|---|---|---|---|
| 准备 | 不限时 | 抽卡、上阵、调站位、派任务、合装备、升科技 | **可以** |
| 战斗 | 30–45 秒 | 放角色大招、放尾兽大招、加速/暂停 | 不可（退出即回滚到本波开始） |
| 结算 | 2–4 秒 | 看掉落与任务奖励 | — |

### 双端会话需求：一个开关解决

手机玩家要能随时收工，PC 玩家不想每波都点一次「开始」。**不要为此做两套流程**——
做一个「自动开始下一波」开关：

- **关**（手机默认）：每波结束停在准备阶段。天然收工点。
- **开**（PC 默认）：结算后 3 秒自动进入下一波，倒计时可打断。

底层波次循环完全一致，只是要不要停。自动模式下依然每波写档。

### 关键技术简化：只在准备阶段存档

不序列化战斗中间态，只序列化准备阶段的完整状态。存档结构因此非常简单（§12），
而玩家**最多等 45 秒就能退出**。

战斗中被打断（手机来电/切后台、PC 强退），回来**回滚到本波开始，不算失败**。
这条对手机端是刚需，对 PC 端是「崩溃不丢进度」的兜底。

### 会话时长

```
单波 ≈ 准备 20~60s + 战斗 30~45s ≈ 1~1.5 分钟
10 波 ≈ 10~15 分钟

手机：任何一波结束都能收工
PC：开自动推进，一次坐 30~60 分钟
```

### 无限流的目标结构

没有「通关」。玩家的成绩就是**本局推到的波次数**。每 10 波是 BOSS 波（§04），
也是天然的收工点。

| 玩家层次 | 目标波次 | 依赖 |
|---|---|---|
| 新手首局 | 15–25 | 看懂属性克制 |
| 熟练 | 40–60 | 五系覆盖 + 成品装备 + 完整羁绊 |
| 核心 | 80–120 | USR + 真武 + 派遣取舍最优化 |

> `TBD` 上表是设计意图，需在 M-1 用批量模拟校准 §04 的成长系数。

### PC 端的内容量要求显著更高

Steam 玩家付费后对角色数量、构筑深度的期待，比免费手游高一个档。同一套系统在手机上
「够玩」，在 Steam 上可能被评为「内容太少」。

影响的是 §09 羁绊与角色池规模：首批 5 组羁绊足够验证机制，但 **PC 首发至少需要
12–15 组羁绊、40+ 角色**。这部分工作量在 M5，要提前计入排期。

### 验收标准

- [ ] 任意波次准备阶段退出程序，重进后状态完全一致（双端各验一次）
- [ ] 战斗中强制杀进程，重进后回滚到本波准备阶段，无数据损坏
- [ ] 单波战斗时长在 30–45 秒区间内（波次 1–100 抽样验证）
- [ ] 自动推进模式下连续跑 30 波无需任何输入，且每波都正确写档

## 02 表现层与操作

### 为什么统一横屏

阵型有前中后三列的纵深，横屏能把这个纵深展开成可读的空间关系；竖屏则要把它压进上下
方向，跟敌人推进方向打架。而且手游自走棋横屏已是惯例（TFT 手游、金铲铲），玩家不需要
重新适应。最重要的是：**一套布局，工作量减半。**

### 屏幕分区

工程既定 `640×360` viewport（16:9），`stretch/mode=viewport` —— 全部按 640×360
渲染后整体放大，像素清晰。手机端额外做刘海安全区内缩。

```
┌──────────────────────────────────────────────────┐
│ HUD：波次 ｜ 下波属性 ｜ 波型 ｜ 覆盖度 ｜ 金币 ｜ 基地血 │
├──────────────────────────────────────────────────┤
│ ┌──┐  ┌─┐┌─┐┌─┐                                   │
│ │基│  │后││中││前│      ● ●    ● ●   ●            │
│ │地│  └─┘└─┘└─┘         敌人 <──── 自右向左推进    │
│ └──┘  ┌─┐┌─┐                ● ●   ●               │
├──────────────────────────────────────────────────┤
│ ◯ ◯ ◯ ◯ ◯  角色大招              尾兽大招 ◉      │
└──────────────────────────────────────────────────┘
```

「前中后」映射为屏幕的**右中左**，与敌人推进方向一致 —— 越靠右的己方单位越先接敌，
空间关系不需要额外解释。基地在最左，被打穿即结束。

### 像素风下的属性表达（关键约束）

属性可辨识是 §03 的硬验收项，但 `640×360` 下一个 16×16 的敌人头顶挂图标只有几像素，
根本看不清。**像素风必须把属性编码进精灵本身：**

- **主色调**：五系各占一个明确色相（火=橙红、风=青绿、雷=明黄、土=褐、水=蓝）
- **轮廓形状**：每系一个可辨识的剪影特征（角、尾、披风形状），
  **不能只靠颜色** —— 色觉障碍 + 缩放后色彩失真
- **描边**：克制关系用描边高亮（可被当前阵容克制的敌人加一圈亮边），
  这是玩家最需要的即时信息

准备阶段的详细信息走 UI 面板，战斗中只保留这三层视觉编码。

### 手动干预点

| 干预点 | 数量 | CD | 作用 |
|---|---|---|---|
| 角色大招 | = 上场人数 | 15–30 秒 | 输出/控制爆发；部分角色自带**聚拢**效果 |
| 尾兽大招 | 1 | 60–90 秒 | 救场底牌，见 §11 |
| 倍速 / 暂停 | 1 | — | 1× / 2× / 3× / 暂停。**暂停时仍可下达大招指令** |

### 吸怪分层保留 `[新设计]`

原版的核心乘法关系必须活着：

```
实际清怪效率 = AOE伤害 × 命中敌人数 × 属性系数
```

中间那个因子必须由玩家决定，否则游戏退化成纯拼数值。既然双端输入精度不同，
就**把这个技巧做成分层的**：

| 端 | 操作 | 效果 |
|---|---|---|
| 手机 / 手柄 | 点一下技能图标 | 自动选取**当前敌人密度最高**的落点释放 |
| PC 鼠标 | 点图标后移动鼠标指定落点，再次点击确认 | 玩家自己判断，可预判走位、卡在敌人即将聚拢的位置 |

自动寻优是**够用但不最优**的 —— 它只看当前帧的密度，不会预判。PC 玩家提前半秒把落点
压在敌人行进路线前方，收益明显更高。这样原版的走位技巧上限在 PC 端回来了，手机端也不残废。

> **关键约束**：自动模式必须能通关到合理波次，不能让手机端变成残疾版。
> 目标是手动操作带来 15–25% 的效率提升，而不是翻倍。

### 拉拽角色的分布要求

给约 4–6 名角色（对应原版小李、卡卡西那批）设计**带位移拉拽的大招**，把范围内敌人拖到
一点。这些角色必须**分散在多个不同羁绊里**，再加上七尾的纯聚拢大招（§11）作为不依赖
抽卡的保底路径 —— 否则抽不到聚拢手段的局就直接废了，这在无限流里是致命的。

### 双端 UI 差异清单

| 项 | PC | 手机 |
|---|---|---|
| 大招落点 | 可手动指定 | 自动寻优 |
| 控件尺寸 | 紧凑 | 热区放大 1.4×，间距加大 |
| 信息密度 | 侧栏常驻详细数值 | 详细数值收进长按/点开的面板 |
| 自动推进 | 默认开 | 默认关 |
| 快捷键 | 数字键放大招、空格暂停 | 无 |
| 拖拽换位 | 鼠标拖拽 | 长按拾起 + 拖拽，带吸附 |

实现上用一个 `InputProfile` 枚举驱动，**不要在 UI 代码里到处写 `OS.has_feature("mobile")`**。
玩家应能在设置里手动切换（PC 接手柄、手机接键鼠都存在）。

### 验收标准

- [ ] 手机端全部按钮热区 ≥ 9mm，单手误触率实测 < 5%
- [ ] 五系敌人在 `640×360` 原生分辨率下可仅凭剪影区分（去色测试）
- [ ] 暂停状态下可完成全部大招操作（含 PC 的落点指定）
- [ ] 纯自动落点玩到的极限波次 ≥ 手动操作的 78%

## 03 属性系统

> **全局地基。这一节的任何改动都会波及其余所有系统。不可改，优先实现。**

### 克制环

```
火 → 风 → 雷 → 土 → 水 → 火
（A → B 表示 A 打 B 造成 200%）
```

### 伤害系数（可调参数）

| 参数 | 默认 | 建议范围 | 说明 |
|---|---|---|---|
| `MULT_COUNTER` | 2.00 | 1.8 – 2.2 | 克制 |
| `MULT_WEAK` | 0.50 | 0.4 – 0.6 | 被克 |
| `MULT_NEUTRAL` | 1.00 | 固定 | 无关属性 |
| `MULT_PHYSICAL` | 1.05 | 1.00 – 1.10 | **全局最敏感旋钮** |

> **`MULT_PHYSICAL` 调参警告**：物理不吃克制、恒定 1.05，是「这波我没配对」的保底补丁。
> **只要往上调到 1.15 以上，堆物理躺赢就会成为最优解，整个属性系统当场作废。**
> 每次改这个值都必须跑回归：物理纯队的极限波次必须显著低于五系队。
> **把这条写进 GUT 测试。**

### 实现约束：Element 挂在伤害实例上，不是单位上

原版中迪达拉本体是土属性但 Q 技能算火系输出。同一角色的不同技能可以是不同属性。

```gdscript
class_name PBDamageEvent extends RefCounted

var source_unit_id: StringName
var amount: int
var element: PBElement.Type    # FIRE | WIND | THUNDER | EARTH | WATER | PHYSICAL
var is_aoe: bool
var tags: Array[StringName]
```

单位身上的 `element` 字段只用于 UI 归类和羁绊判定的默认值。一开始写对，后面才能扩展
「多属性角色」「属性转换 buff」「装备附魔改属性」。

### UI 表达（原版最大的短板，必须补）

原版的克制关系要点开技能说明才能看到，玩家靠背。这是复刻版投入产出比最高的一处改进。

- **下一波属性预告常驻 HUD**，提前 1 波显示
- **覆盖度自动结算**：准备阶段显示「当前阵容对下一波的克制覆盖：`2/5`，风系空缺」
- **伤害飘字区分**：克制用放大 + 上扬，被克用缩小 + 灰化。不能只靠数字大小
- **敌人视觉编码**：见 §02 的像素风三层编码

### 验收标准

- [ ] 全物理阵容的极限波次 < 五系均衡阵容的 70%
- [ ] 单系阵容无法通过完整的 5 波轮转（在同等战力下必然卡波）
- [ ] 新手在无教程情况下，3 波内能自行说出「属性要配对」

## 04 波次与难度曲线

### 属性轮转

沿用原版顺序，无限循环：

```gdscript
const WAVE_ELEMENTS := [FIRE, THUNDER, WATER, EARTH, WIND]
func wave_element(n: int) -> int:
	return WAVE_ELEMENTS[(n - 1) % 5]
```

每 5 波一个完整周期，**玩家必须长期维持五系覆盖** —— 这是阻止阵容固化的唯一机制。

| 波次 mod 5 | 敌方 | 需要的输出 | 废掉的输出 |
|---|---|---|---|
| 1 | 火 | 水 | 风 |
| 2 | 雷 | 风 | 土 |
| 3 | 水 | 土 | 火 |
| 4 | 土 | 雷 | 水 |
| 0 | 风 | 火 | 雷 |

### 成长公式

```
HP(n)     = HP_BASE × GROWTH^(n−1) × TypeHpMult
ATK(n)    = ATK_BASE × GROWTH^(n−1)
Count(n)  = min(floor((COUNT_BASE + n × COUNT_RATE) × TypeCountMult), COUNT_CAP)
Reward(n) = GOLD_BASE + GOLD_RATE × n        # 线性，不跟血量指数走
```

| 参数 | 默认 | 范围 | 说明 |
|---|---|---|---|
| `HP_BASE` | 120 | 80–200 | 1 波普通怪血量 |
| `ATK_BASE` | 10 | 6–18 | 1 波普通怪攻击 |
| `GROWTH` | 1.125 | 1.10–1.15 | **整条曲线的主控** |
| `COUNT_BASE` | 8 | 6–10 | 1 波怪物数 |
| `COUNT_RATE` | 0.5 | 0.3–0.8 | 每波增量（波型倍率在此之后叠加） |
| `COUNT_CAP` | **48** | 见下 | **待决策** |
| `GOLD_BASE` | 45 | 30–60 | 波次基础奖金 |
| `GOLD_RATE` | 6 | 4–10 | 每波增量 |

### `COUNT_CAP` 待决策 `TBD`

原版魔兽后期一屏几十个怪，本案早期版本（面向微信小游戏）压到 24 是性能妥协。
Godot 上性能不是问题，但**像素风 `640×360` 有新的约束**：

| 候选 | 视觉 | 风险 |
|---|---|---|
| 24 | 每个单位清晰可辨 | 后期难度全靠血量，「潮水感」不足 |
| **48（建议）** | 密集但仍可分辨个体 | 需要认真做 z-order 与轻微散布 |
| 96+ | 真正的潮水感 | `640×360` 下会糊成一团，属性无法辨识 |

**建议从 48 起步，M0 出画面后用真机观感定夺。** 决策依据是「去色后能否区分五系剪影」
（§02 验收项）—— 那一条通不过，数量就必须降。

> **`COUNT_CAP` 绝不能按平台分档。** 手机和 PC 跑的是同一份模拟，否则双端难度不同、
> 排行榜没意义。性能差异只在渲染层吸收（`MultiMeshInstance2D` 合批、特效降级），
> **sim 层完全不知道自己跑在什么设备上**。

### 波型交替 `[新设计]`

如果敌人永远又多又硬，AOE 会永远碾压单体输出，构筑就收敛了。用**波型**把两种价值分开：

| 波型 | 频率 | 数量 | 单体血量 | 谁的高光 |
|---|---|---|---|---|
| 常规波 | ~60% | ×1.0 | ×1.0 | 均衡 |
| **潮水波** | ~25% | ×2.2 | ×0.45 | AOE + 聚拢大招 |
| **精英波** | ~15% | ×0.3 | ×4.0 | 单体爆发、破甲、吸血 |
| BOSS 波 | 每 10 波 | 1–3 | ×8.0 | 爆发 + 尾兽底牌 |

波型在**准备阶段提前公示**，和属性预告并列。玩家因此每波都在做一次小的阵容微调判断 ——
这一波要 AOE 还是单体、要不要为它换人。这是原版完全没有的一层。

### 压力曲线

无限流的设计核心不是「难度多高」，而是**玩家战力增速必须略低于怪物增速**，
这样一定会卡住，卡住的波次就是分数。

```
压力(n) = 怪物强度(n) / 玩家理论战力(n)

设计目标：压力缓慢上升，呈锯齿状
  ↗ 每波怪物 ×1.125
  ↘ 玩家在关键节点跳跃式变强（合成真武 / 抽到 USR / 凑齐羁绊 / 升满一支科技）
```

锯齿的「齿」就是玩家的爽点。要让每个大成长节点都能**肉眼可见地把压力压下去几波**，
然后重新爬升。**这条曲线是整个数值配平的目标函数。**

### BOSS 节奏

| 波次 | 类型 | 倍率 | 特点 |
|---|---|---|---|
| `n % 10 == 0` | BOSS 波 | ×8 HP，数量 1–3 | 带机制；**清空后为存档/收工点** |
| `n % 50 == 0` | 大 BOSS | ×20 HP | 多阶段，**属性在阶段间切换** —— 强制备齐多系 |

### 50 波后的机制化加压

原版被批评「无尽只靠数值堆叠」。50 波后注入机制性变化：

- **混合属性波**：一波内混编两种属性，强迫同时覆盖两系
- **无属性精英**：不吃克制加成，只能靠纯输出磨（考验物理位的存在价值）
- **波次负面词条**：本波随机附加一条（治疗减半 / 大招 CD +50% / 后排受额外伤害），
  准备阶段可见

> `TBD` 词条池设计留到 M5，但数据结构要在 M-1 就预留 `wave_modifiers: Array` 字段。

### 验收标准

- [ ] 压力曲线在 1–120 波区间单调上升，无断崖也无平台期
- [ ] 同屏单位数在任意波次不超过 `COUNT_CAP`，且双端逻辑数量完全一致
- [ ] 每个 BOSS 波都能被「刚好达标」的阵容击败，误差 ±15%
- [ ] 纯 AOE 阵容在精英波明显吃力，纯单体阵容在潮水波明显吃力（两者极限波次差 < 15%）

## 05 人口与双站台

原版把**羁绊和战力彻底解耦**：待命台的忍者不参战、不占出战人口，但**羁绊全额生效**。
于是出战人口只用来放输出，待命台变成羁绊仓库。高阶玩法就是「用最少的上场位撑起最多的羁绊」。

| | 出战席 | 待命台 |
|---|---|---|
| 参战 / 产生伤害 | 是 | 否 |
| 占出战人口 | 是 | 否 |
| 羁绊生效 | 是 | **是（全额）** |
| 可放大招 | 是 | 否 |
| 可被派遣做任务 | 否 | **是**（§06） |
| 布局 | 前 / 中 / 后三列（屏幕右→左） | 独立格子 |

| 参数 | 初始 | 上限 | 升级方式 |
|---|---|---|---|
| 出战人口 | 4 | 10 | 人口科技，每级 +1 |
| 待命台格数 | 3 | 6 | 人口科技，每 2 级 +1 |
| 前 / 中 / 后 列容量 | 2 / 2 / 2 | 4 / 3 / 3 | 随出战人口解锁 |

> **原版的漏洞**：如果待命台格子够多且羁绊全额生效，最优解永远是「能凑羁绊的卡全塞进去」，
> 不存在决策。本案的解法在 §06。

## 06 任务派遣 `[新设计]` `[核心张力]`

### 原版的问题

原版规则是「待命台放至少 2 人才结算任务奖励」。攻略把它列为新手第一条，说明这是个
**忘了就白给**的操作税 —— 没有人会「战略性地选择不做任务」，它不产生任何决策。

### 改造后的规则

派遣是一个**主动动作**：准备阶段，玩家把待命台的忍者标记为「出任务」。

```
派遣期间（本波内），该忍者的羁绊不生效。
波次结算后返回待命台，羁绊恢复。
```

于是每一波玩家都要回答同一个问题：

> **这一波，我要羁绊，还是要钱？**

任务等级越高，需要派出的人越多，羁绊损失越大。这跟 §07 的「经济位 = 战力空位」是同构的
取舍，但作用在**羁绊层**，形成第二条张力轴。

### 任务表

每波结束自动刷新一个任务；可花金币重刷。

| 等级 | 刷新权重 | 需派遣 | 金币 | 附加掉落 |
|---|---|---|---|---|
| C | 40% | 2 人 | 60 + 8n | — |
| B | 27% | 2 人 | 100 + 14n | 10% R 配件 |
| A | 18% | 3 人 | 160 + 22n | 35% R 配件 |
| S | 10% | 3 人 | 250 + 35n | 100% R 配件，15% SR 配件 |
| SSS | 5% | 4 人 | 400 + 55n | 100% SR 配件，20% 合成卷轴 |

`n` = 当前波次。重刷费用 `50 + 5n`，每波可重刷次数不限（为高阶玩家保留「赌高收益」的空间）。

### 连锁效果

- **SSS 任务需要 4 名待命**，而待命台初始只有 3 格 → 人口科技有了明确的追求目标
- 玩家会刻意准备**「工具人忍者」**：羁绊贡献低但可以随时派出去的卡。
  **R 卡因此有了后期价值**，不再是纯废牌
- BOSS 波前一波，玩家倾向**不派任务、保满羁绊** —— 节奏自然产生起伏

### 验收标准

- [ ] 存在至少 3 种可行的派遣策略（全力经济 / 全力羁绊 / BOSS 波前收手），极限波次差异 < 20%
- [ ] 不派任务能推进但明显吃力；一直派满 SSS 也会因羁绊缺失卡波
- [ ] 准备阶段能一眼看出「派出后羁绊会掉几档」

## 07 经济系统

| 来源 | 触发 | 公式 | 占位 | 风险 |
|---|---|---|---|---|
| 金币科技 | 每 0.5 秒 | `5 × (1 + 0.35 × Lv)` | 否 | 无风险，一次性投资 |
| 波次奖金 | 每波结算 | `45 + 6n` | 否 | 无风险 |
| 角都 | 每波结算 | `Lv × 85 × k^−1.5` | 出战/待命 | 低，与战斗脱钩 |
| 纲手 | 每次击杀 | EV `+13` | 出战 | 高，打不动就断粮 |
| 任务 | 每波结算 | 见 §06 | 占待命 + 羁绊 | 中，代价是羁绊 |

### 纲手（击杀流）

```
击杀掉落分布：50% → +35 ｜ 30% → −15 ｜ 20% → 0
EV = 0.50×35 + 0.30×(−15) + 0.20×0 = +13 / 击杀
```

**原版保留不动。** 它是稳赚的，却包装成会看到扣钱的老虎机 —— 玩家记住负反馈、实际长期
盈利，用体感波动换注意力投入。这是老练的设计，别去「修」它。

### 角都（回合流）

```
单个角都收益 = 等级 × 85
第 k 个角都的系数 = k^(−1.5)
k=1 → 1.000 ｜ k=2 → 0.354 ｜ k=3 → 0.192 ｜ k=4 → 0.125
```

> **改动：角都取消输出能力。** 原版角都既是回合经济位，又是雷系 AOE 输出第二名 ——
> 一个位置交付两份价值，这是原版流派单一的直接原因。本案改为**纯经济卡，无 AOE 技能**；
> 递减也从原版的减半改成 `k^−1.5`（更陡）。这样「上角都」是真实的战力牺牲。

### 科技树

| 分支 | 效果 | 等级 | 价格曲线 |
|---|---|---|---|
| 金币 | 每 0.5 秒收益 +35%/级 | 0–20 | `120 × 1.35^Lv` |
| 人口 | 出战 +1/级，待命 +1/2级 | 0–6 | `300 × 1.8^Lv` |
| 攻击 | 全局攻击 +6%/级 | 0–15 | `200 × 1.4^Lv` |
| 防御 | 基地减伤 +4%/级 | 0–10 | `180 × 1.45^Lv` |

> `TBD` 价格曲线是占位值。真正要配的是**「第一个金币科技的回本波次」**——
> 建议控制在 3–4 波回本，让「优先升经济」成为正确但不无脑的选择。

### 核心张力：经济位 = 战力空位

经济投入有一条**硬下限**：低于某个清怪速度，所有经济收益归零（打不死 → 纲手不产出 →
漏怪掉血 → 出局）。所以经济曲线不自由，被「当前波次生存线」压着，而这条线随波次上升。

配平时要保证：**纯经济开局在第 8–12 波必然崩盘**，纯战力开局在 20 波左右因缺钱停滞。
最优解在中间且随流派浮动。

## 08 抽卡与稀有度

| 稀有度 | 技能数 | 定位 |
|---|---|---|
| R | 1–2 | 前期过渡；**后期作为派遣工具人保留价值**（§06） |
| SR | 2–3 | 阵容中坚，主流羁绊核心，部分可用到终局 |
| SSR | 3 | 中后期核心战力 |
| USR | 3 + 专属机制 | 数值碾压，决定极限波次上限 |

### 概率表

单抽价格固定 **150 金**；后期收入增长 = 抽卡自由度增长。

| 波次段 | R | SR | SSR | USR |
|---|---|---|---|---|
| 1 – 10 | 70% | 27% | 3% | 0% |
| 11 – 20 | 55% | 36% | 8.5% | 0.5% |
| 21 – 30 | 40% | 42% | 16% | 2% |
| 31 – 50 | 25% | 45% | 25% | 5% |
| 51 + | 12% | 43% | 33% | 12% |

## 09 羁绊系统

### 硬性规范：每个羁绊至少有一档是功能解锁

原版的羁绊之所以有意思，是因为推荐组合卖的不是数值，而是**一套完整的操作 combo**——
凯班给你聚怪（木叶旋风），第七班给你聚怪 + 团队增益（神威 + 心灵之火）。玩家凑齐羁绊
之后，**玩法本身改变了**，而不只是数字变大。

数值型羁绊最好做也最没意思。**本案要求：每个羁绊的最高档必须解锁一个机制**
（新技能、新交互、新站位规则），不能是「攻击 +25%」。

### 生效规则

- 出战席与待命台**双场景全额生效，无衰减**（原版设计，保留）
- 派遣出去做任务的忍者**羁绊暂时失效**（本案新增，§06）
- 同一角色可同时属于多个羁绊

### 档位规范

| 羁绊规模 | 档位 | 档位内容要求 |
|---|---|---|
| 小队型（3–4 人） | 2 / 3 / 4 | 2 档数值 → 3 档**功能** → 4 档强化功能 |
| 阵营型（6–10 人） | 2 / 4 / 6 | 2 档数值 → 4 档数值 → 6 档**功能** |
| 属性型（同系） | 2 / 4 | 纯数值，作为兜底羁绊，允许无功能 |

### 首批实现（5 组，验证机制用）

| 羁绊 | 成员 | 3 档功能 |
|---|---|---|
| 凯班 | 迈特凯、李洛克、天天、日向宁次 | 李洛克大招获得**聚拢**效果 |
| 第七班（原） | 卡卡西、宇智波带土、野原琳 | 卡卡西大招升级为**单点吸附**，琳获得团队增益光环 |
| 猪鹿蝶 | 山中井野、奈良鹿丸、秋道丁次 | 鹿丸大招**定身**，井野控制期间敌人受伤 +30% |
| 木叶三忍 | 自来也、纲手、大蛇丸 | 纲手金币收益提升，且**负收益不再触发** |
| 砂忍三姐弟 | 我爱罗、手鞠、勘九郎 | 我爱罗获得**持续减速力场** |

> `TBD` 完整羁绊清单（晓、五影、历代火影、鹰小队、日向、人柱力等）留到 M5。
> PC 首发需要 12–15 组，见 §01。

## 12 存档与断点

### 存档时机

- **自动存档**：每波战斗结算完成、进入准备阶段时
- **手动存档**：不提供（避免玩家误解为可读档反悔）
- **战斗中断**：回滚到本波准备阶段，不惩罚

### 存档结构

```gdscript
# 序列化为 JSON，存 user://run_save.json
{
	"version":      int,
	"wave_index":   int,
	"gold":         int,
	"base_hp":      int,
	"roster":       [{ "char_id":, "star":, "level":, "equip_ids": [] }],
	"deployed":     [{ "char_id":, "col":, "slot": }],   # 出战席
	"standby":      [{ "char_id":, "slot": }],           # 待命台
	"dispatched":   [char_id],                           # 本波派遣中
	"tech":         { "gold":, "pop":, "atk":, "def": },
	"tailed_beast": { "id":, "level":, "cd_remaining": },
	"inventory":    { "parts": {}, "items": [], "scrolls": },
	"active_quest": { "grade":, "seed": },
	"rng":          { "gacha":, "quest":, "combat": },   # 各存 state
	"stats":        { "kills":, "gold_earned":, "elapsed_ms": }
}
```

### 随机数：Godot 自带的正好够用

`RandomNumberGenerator` 同时暴露 `seed` 和 `state`，而 **`state` 是可读可写的整数**——
直接存进档、读档时赋回去即可，不需要自己实现 PRNG。

```gdscript
# 存
save["rng"]["gacha"] = _rng_gacha.state
# 读
_rng_gacha.state = save["rng"]["gacha"]
```

> **绝对不要用 `randi()` / `randf()` 这些全局函数** —— 它们走共享的全局 RNG，状态不可控。
> sim 层必须持有自己的 RNG 实例。

三条独立随机流：`_rng_gacha`（抽卡）、`_rng_quest`（任务刷新与波型）、
`_rng_combat`（掉落与暴击）。**分开后，某一路的调用次数变化不会污染其他路** ——
否则改一次战斗掉落逻辑就会让所有旧存档的抽卡序列全变。

为什么要这么较真：读档后抽卡结果若会变，玩家就会用「退出重进」刷好卡；
将来要做「每日种子挑战」或战报回放也全依赖这一条。

### 存储

- 路径 `user://run_save.json`，用 `FileAccess` + `JSON.stringify`。
  **存 JSON 不存二进制** —— 可读、可手改调试、跨版本迁移容易
- 体积约 3–8KB，两端都无压力
- 用**原子写**（先写 `.tmp` 再 rename），防止写一半掉电导致存档损坏
- **版本迁移**：`version` 字段必须从第一天就有。无限流的存档生命周期可能跨越多个版本
- `TBD` Steam 云存档：Auto-Cloud 配置 `user://` 目录即可，几乎零成本

### 验收标准

- [ ] 准备阶段退出 → 重进，全部状态位逐字段一致
- [ ] 战斗中杀进程 → 重进回滚到本波开始，无异常
- [ ] 读档后连续抽卡 10 次的结果，与不读档时完全一致
- [ ] 旧版本存档在新版本能正确迁移或安全降级

## 13 排行榜与每日挑战

无限流天然自带排行维度 —— 比谁推得深。这是砍掉 PVP 之后的竞争维度，
成本只有真 PVP 的零头，不需要实时同步、不需要匹配池、不怕冷启动。

| 阶段 | 形态 | 防作弊 | 成本 |
|---|---|---|---|
| **首版** | 本地历史最佳 + 每日种子挑战 | 不需要 | 零 |
| PC 发行 | **Steam Leaderboards** | 存档签名 + 异常值过滤 | 低，无需自建后端 |
| 二期 | 跨端全服榜 + 赛季重置 | 服务端校验 | 中，要自建后端 |
| 三期 | 战报回放 / 幽灵对战 | 操作序列重放验证 | 高 |

### 每日种子挑战 `[新设计]`

既然 RNG 已经是确定性的（§12），**用日期当种子生成一局，全世界玩家当天面对完全相同的
抽卡序列、任务序列和波型序列。**

实现只需要 `seed = hash(date_utc)` 传给三条 RNG 流，其余系统零改动。换来：

- 可比性极强的竞争 —— 大家条件一样，纯比操作和决策
- 天然的每日回访理由（PC 和手机都需要）
- 社区讨论话题（「今天这个种子怎么开局」），对 Steam 口碑传播特别有用

**建议放进 M4**，跟存档一起做。

## 14 技术架构

### 目录规划（在既有 `src/` 约定下扩展）

```
src/
├── core/            # 纯逻辑，零引擎依赖，全部 RefCounted
│   ├── sim/         #   定帧战斗模拟
│   ├── rules/       #   属性克制、羁绊、装备、经济结算
│   ├── rng/         #   三条 RandomNumberGenerator 流
│   └── save/        #   序列化与版本迁移
├── view/            # Node2D，只读 core 状态来渲染
├── ui/              # 控件，按 InputProfile 分叉
└── tools/           # headless 批量模拟、数值导出
data/                # 自定义 Resource（.tres）：角色 / 羁绊 / 装备 / 尾兽
scenes/              # .tscn
tests/               # GUT 用例（core 的单元测试全在这）
```

### 铁律：`src/core/` 里不许出现任何引擎 API

不继承 `Node`（用 `RefCounted`）、不 `get_node()`、不访问 `SceneTree`、不读 `delta`、
不调用全局 `randi()`。`core` 只有数据进、数据出。

守住这一条，同时白拿四样东西：

1. **确定性** —— §12 的存档回滚和每日种子全靠它
2. **可单元测试** —— GUT 已就位，`tests/` 直接测 `core`，不用起场景
3. **可 headless 批量模拟** —— M-1 校数值的前提
4. **可换渲染层**

破坏这条的成本极高：一旦 sim 里混进场景树访问，上面四样会一起失效，
拆回来基本等于重写。

> **建议在 `scripts/check.ps1` 里加一个阶段**：grep `src/core/` 目录，
> 出现 `get_node`、`randi(`、`randf(`、`delta`、`extends Node` 就报错。
> 这条防线自动化之后基本不会被破坏。

### GDScript 的两条硬约束

**1. 全面静态类型**（工程规范已有此条，此处强调其性能意义）

带类型标注的 GDScript 走**类型化指令**，性能明显高于动态版本 —— M-1 要跑几千局批量
模拟，这个差距会直接变成等待时间。

**2. sim 层控制对象分配**

GDScript 每帧创建大量临时对象会触发频繁的引用计数开销。战斗 sim 里：

- 敌人/子弹用**预分配数组 + 空闲索引栈**，不要每次 `.new()`
- 批量数值用 `PackedInt32Array` / `PackedFloat32Array`，不用 `Array`
- 伤害事件用对象池复用，别为每次命中新建实例

> 如果 M-1 实测批量模拟慢到无法接受（比如 1000 局要跑几十分钟），备选是把 `src/core/sim`
> 单独改写成 C#，view 保持 GDScript。**但先别提前优化** —— 48 单位 × 20 tick/s 的规模，
> 静态类型 GDScript 大概率够。

### 定帧与倍速

```
逻辑：固定 20 tick/s，由 _physics_process 驱动自己的累加器
渲染：按显示帧率插值，与逻辑帧解耦
倍速：只改「每渲染帧步进多少个 tick」，不改 tick 时长
      1× → 每秒 20 tick ｜ 2× → 40 tick ｜ 3× → 60 tick
```

这样倍速不会引入任何数值差异 —— 3 倍速和 1 倍速跑出来的结果**逐 tick 完全一致**。

> 如果用 `Engine.time_scale` 或直接乘 `delta`，倍速下的浮点累积误差会让结果漂移，
> **存档回滚和每日种子挑战全部失效**。从第一天就定帧，后期改代价极高。

### 数据表用自定义 Resource

`class_name PBCharacter extends Resource` + `@export` 字段，每个角色/羁绊/装备存一个 `.tres`：

- 白送检查器编辑界面，不用自己搭工具
- `.tres` 是文本格式，**git diff 可读**
- 类型安全，字段名写错编辑器直接报
- 换皮时只改 `data/` 和语言表

代码里通过 `id` 索引，**不出现任何角色名字符串**。显示名走 `name_key` → 语言表。

### 渲染优化

- **对象池**：敌人节点、飘字、特效全部池化，战斗中零新建
- **飘字合并**：同 tick 同目标的多次伤害合并成一条
- **`MultiMeshInstance2D`**：手机端对密集同类敌人合批，是双端难度一致的前提（§04）
- **特效层数按平台降级**：手机端减少粒子与叠加层，但**不影响任何逻辑数值**

### 双端导出

| 目标 | 注意 |
|---|---|
| Windows | 主要开发与调试目标，优先做 |
| Android | 需要 Android SDK + 签名密钥；触控 UI 与热区**在真机上验，模拟器不算数** |
| iOS `TBD` | 需 Mac 与开发者账号，国内上架需版号。**建议延后** |

**建议 PC 先行。** 调试链路短、迭代快，玩法定型后再适配手机 ——
反过来做会在触屏适配上反复返工。

### 生命周期处理

- 手机端监听 `NOTIFICATION_APPLICATION_PAUSED`：立即暂停并写档
- PC 端监听 `NOTIFICATION_WM_CLOSE_REQUEST`：写档后再退出
- 失焦时自动暂停（可在设置里关，PC 玩家可能想挂着看）
