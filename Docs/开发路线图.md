## M-1 详解：为什么必须先做

施工策划案 §04 的 `GROWTH = 1.125` 和 §01 的目标波次表（新手 15–25 / 熟练 40–60 /
核心 80–120）是**互相绑定的设计意图，但都是拍脑袋的初值**。

**在这两个数校准之前，后面所有数值都别细配，会白做。**

因为 `src/core/` 是零引擎依赖的，M-1 不需要任何画面就能跑：

```powershell
F:\Godot_PJ\_engine\4.7.2\godot_console.exe --headless --path . --script res://src/tools/batch_sim.gd
```

> 命令行一律用 `godot_console.exe`，`godot.exe` 的 stdout 不回传终端。

### M-1 的产出

一张 CSV，列出不同参数组合下的结果分布：

| 列 | 含义 |
|---|---|
| `growth` | 测试的 `GROWTH` 值 |
| `strategy` | 模拟的玩家策略（五系均衡 / 纯物理 / 纯经济 / 纯战力 / …） |
| `wave_reached` | 卡波的波次 |
| `runs` | 该组合跑了多少局 |
| `p50` / `p90` | 波次分布的中位数与 90 分位 |

### M-1 要回答的四个问题

1. **`GROWTH` 定多少**，能让三档玩家分别落在 15–25 / 40–60 / 80–120
2. **纯物理阵容的极限波次是否 < 五系阵容的 70%**（§03 验收项）
3. **纯经济开局是否在 8–12 波崩**（§07 配平目标）
4. **不同派遣策略之间的差异是否在 20% 以内**（§06 验收项）

### M-1 的最小实现范围

只需要这些，其余全部略过：

- 属性克制表与伤害结算（§03）
- 波次成长公式与波型（§04）
- 一个极简的「玩家战力」抽象（不需要真的实现羁绊/装备，用一条成长曲线代替）
- 三条 RNG 流（§12）
- 策略脚本：几个写死的 AI 决策函数，代表不同玩法流派

**不要实现**：UI、动画、真实的技能效果、装备合成树、完整角色表。

## 风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| **M2 的「羁绊 ↔ 金币」取舍不好玩** | 本案最大原创设计失败 | M2 做完立刻找 5–10 人实测，不要等到 M5。失败就退回原版的简单规则，或另找张力轴 |
| **像素风下属性辨识度不够** | §03 的地基失效，游戏退化成拼数值 | M0 做去色剪影测试；不过就降 `COUNT_CAP`、加大精灵尺寸 |
| **GDScript 批量模拟太慢** | M-1 迭代周期拉长 | 先测实际耗时。真不行就把 `src/core/sim` 改写成 C#，view 保持 GDScript |
| **PC 内容量不足被差评** | Steam 口碑 | M5 提前排期，12–15 组羁绊、40+ 角色是底线 |
| **火影 IP 商业化风险** | 无法商业发行 | 角色数据全在 `data/` 的 Resource 里，代码只认 id。换皮 = 改表 + 换素材，`src/` 一行不动 |

## 已定的架构铁律（不要违反）

这几条是后面所有能力的地基，破坏任何一条都要付重写的代价。详见施工策划案 §14。

1. **`src/core/` 零引擎依赖** —— 不 `extends Node`、不 `get_node()`、不读 `delta`、
   不调全局 `randi()`
2. **定帧 20 tick/s**，倍速只改每帧步进的 tick 数，绝不用 `Engine.time_scale` 或乘 `delta`
3. **三条独立 RNG 流**（gacha / quest / combat），各自持有 `RandomNumberGenerator` 实例，
   `state` 存进档
4. **`element` 挂在伤害事件上**，不挂在单位上
5. **代码里不出现角色名字符串**，一律走 `id` + `name_key`
6. **`COUNT_CAP` 不按平台分档**，性能差异只在渲染层吸收
